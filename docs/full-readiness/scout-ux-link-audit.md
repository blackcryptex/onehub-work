## Confirmed findings

### P0: No Scout P0 UX blocker found from public/source link inspection

I did not find a confirmed public route that both appears as a visible major MVP link and returns a hard 404, except `/event-dreamer`, which is generated by the centralized dashboard helper but not visibly linked as a standalone public destination in the current homepage/header/footer.

User-facing impact: The site is not obviously dead from the public entry points. A signed-out visitor can reach core public pages, help/legal/support pages, marketplace discovery, event wizard, pro setup, and provider start.

Narrow next action: Keep this as PARTIAL, not COHERENT, because several P1/P2 navigation and clarity defects remain before private-pilot/live confidence.

### P1: Event Dreamer dashboard route helper points to a missing route

Evidence:

- `apps/web/src/lib/routes.ts:150-151` maps `EVENT_DREAMER` dashboard to `/event-dreamer`.
- Source route inventory shows `apps/web/src/app/event-dreamer/create/page.tsx`, but no `apps/web/src/app/event-dreamer/page.tsx`.
- Canonical smoke check returned `/event-dreamer` -> 404.
- Homepage links Event Dreamer to `/event-dreamer/create` at `apps/web/src/app/page.tsx:73-75`, which works.

Finding: Event Dreamer has a working creation route, but the centralized dashboard helper can send an authenticated Event Dreamer user to a missing dashboard.

User-facing impact: An Event Dreamer who signs in or is routed by role dashboard logic may hit a 404 instead of the saved dream/create page. This is confusing and makes the role feel unfinished.

Narrow next action: Route `EVENT_DREAMER` to `/event-dreamer/create` or add a real `/event-dreamer` dashboard/index page.

### P1: Vendor/venue signed-out dashboard redirects lose the intended role dashboard callback

Evidence:

- Canonical `/vendor/dashboard` extracted as a sign-in page with create-account link `https://www.1hubevents.com/signup?callbackUrl=%2Fapp`.
- Canonical `/venue/dashboard` extracted the same sign-in page with callback `/app`.
- Source `apps/web/src/lib/routes.ts:146-149` expects vendor dashboard `/vendor/dashboard` and venue dashboard `/venue/dashboard`.
- Source `apps/web/src/app/app/page.tsx:41-55` later reroutes VENDOR/VENUE users from `/app` to dashboard or onboarding, but the visible auth page does not preserve the original role-specific destination.

Finding: Signed-out users who directly open vendor/venue dashboards see a generic `/app` callback in sign-in/sign-up. The eventual app redirect may recover after role lookup, but the user-facing auth link does not explain or preserve the vendor/venue destination.

User-facing impact: Providers can feel bounced into a generic app path rather than their business dashboard. This is especially risky for vendors/venues responding to leads or onboarding links.

Narrow next action: Preserve the requested path in the auth callback for `/vendor/dashboard` and `/venue/dashboard`, or show role-specific copy explaining that sign-in will continue to the provider dashboard/onboarding.

### P1: Header search input is visible but has no action or results surface

Evidence:

- No form, submit handler, search route, label, or results destination is attached in that component.

User-facing impact: Users may try searching vendors, events, help, or pages and get no response. This creates immediate frustration and makes navigation feel broken even when core links work.

Narrow next action: Hide the search box until a real search destination exists, or wire it to a defined route such as marketplace/help search with clear placeholder text.

### P1: Public marketing copy overpromises legal/payment maturity in several places

Evidence:

- `apps/web/src/app/features/page.tsx:19-22` says AI contracts are "legally sound".
- `apps/web/src/app/features/page.tsx:35-37` says held funds are held safely until services are delivered to satisfaction.
- Homepage `apps/web/src/app/page.tsx:111-114` says "Held funds pending release and easy sign-in for peace of mind".
- Legal/payment help content is more guarded: `apps/web/src/lib/help-content.ts:300-326` explicitly says payment readiness is guarded/private-pilot/test-mode and not a public launch, escrow, payout, refund, or legal guarantee.
- Pro event workspace copy is also guarded: `apps/web/src/app/pro/planner/vault/[eventSlug]/page.tsx:1425-1447` separates payment readiness from budget and blocks payment until contract state supports it.

Finding: Public marketing language is stronger than the guarded product/legal language elsewhere. The homepage/features pages can imply legal correctness and escrow-like safety before users reach the guarded readiness disclaimers.

User-facing impact: Users may misunderstand OneHub as already providing legal assurance, escrow, or satisfaction-guaranteed money safety. That increases trust, money, and legal expectation risk.

Narrow next action: Align public pages with the guarded wording used in help/event/payment surfaces. Replace "legally sound" and broad held-funds assurances with private-pilot/test-mode/readiness language until legal/payment launch approval exists.

### P2: Vendor/venue dashboard tabs are local-only panels, not addressable routes

Evidence:

- Vendor dashboard `apps/web/src/components/vendor/Sidebar.tsx:34-40` defines button tabs for Overview, Leads, Payments, Calendar, Messages, Settings and updates local state.
- Venue dashboard `apps/web/src/components/venue/Sidebar.tsx:15-40` similarly defines local button tabs; venue `UIRoute` omits `payments` but source imports `DollarSign` in `apps/web/src/components/venue/Dashboard.tsx:23` and speaks about booking/payment readiness in overview copy.
- Pro planner dashboard `apps/web/src/components/pro-planner/Sidebar.tsx:41-55` also uses local state tabs for many internal sections.

Finding: Role dashboards behave like single-page local tabs rather than deep-linkable routes. This is not a broken link, but the state is not shareable/bookmarkable and may reset on refresh.

User-facing impact: Users cannot easily send a teammate to "Vendor > Leads" or refresh on "Payments" without landing back on overview. It reduces operational usefulness once the product has real lead/payment/admin workflows.

Narrow next action: For MVP, keep local tabs if intentional, but add clear in-page labels and consider URL query/hash state for high-value tabs like leads, messages, payments, and settings.

## Verdict

PARTIAL

OneHub has meaningful route coverage and many major MVP links point to real pages or protected sign-in flows. The current UX is not BROKEN overall, but it is not fully COHERENT for private-pilot/live readiness because several visible surfaces still create user confusion: one role dashboard helper points to a 404, search appears usable but has no behavior, provider auth/onboarding callbacks are generic or client-dependent, public money/legal copy is stronger than guarded product reality, and the pro workspace is dense enough to overwhelm new users.

## Recommended next action for Atlas

Route a narrow implementation pass for the priority fix order above, starting with the Event Dreamer dashboard route, header search removal/wiring, guarded marketing copy, and vendor/venue auth callback clarity. Then ask Sentinel to run authenticated route/link smoke tests with seeded users for DIY, client, pro planner, vendor, venue, and admin before this audit is treated as final QA.
