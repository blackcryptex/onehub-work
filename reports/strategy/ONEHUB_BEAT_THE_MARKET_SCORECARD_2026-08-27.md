# OneHub beat-the-market scorecard and MVP promise baseline

Date: 2026-08-27
Owner lane: Scout, Phase 0 positioning/scorecard
Scope: Convert the uploaded competitor analysis, the approved beat-the-market plan, and existing OneHub stabilization reports into an execution-ready user-facing superiority scorecard.

Boundary: This report is a product promise and acceptance baseline only. It does not approve public launch, live payments, Stripe activation, legal claims, production changes, outbound email/SMS activation, or final release.

## Verdict

PARTIAL.

OneHub has the right market-winning direction: it should not try to beat Zola at registry, Minted at invitations, or The Knot/WeddingWire at directory scale. The credible OneHub promise is stronger execution and trust after discovery: provider-backed proposals, contracts, protected payment readiness, milestone accountability, communication truth, crisis recovery, and admin oversight.

Current OneHub evidence shows a recognizable private-pilot trust spine, but it is not yet good enough to claim superiority. The strongest current surfaces are Pro Planner commercial workspace, admin trust-risk oversight, selected event discovery/request flow, safe payment guardrail copy, and role dashboards. The main gaps are provider-backed proposal handoff, cross-role commercial record visibility, authenticated marketplace coherence, invite/outbound truth, client pending-share usefulness, and live-payment/legal boundaries.

## OneHub promise in simple language

OneHub helps people run the event, not just plan the event.

The MVP promise should be:

"OneHub keeps the people, commitments, money-readiness, deadlines, and problems for an event in one trusted operating flow: find a provider, get a provider-backed proposal, approve the scope, generate the contract, confirm signatures, prepare protected payment steps safely, track milestones, communicate clearly, and recover when something goes wrong."

Shorter user-facing version:

"Plan the event, prove the commitments, and keep execution on track."

What OneHub should NOT promise yet:
- Not "better wedding websites than Minted or Joy."
- Not "bigger vendor marketplace than The Knot or WeddingWire."
- Not "better registry than Zola."
- Not "live payments/escrow are enabled" unless credentials, legal/payment approval, Stripe configuration, and Sentinel verification prove it.
- Not "emails/SMS/invites were sent" unless provider-backed delivery exists and is verified.
- Not "public-launch ready" until Sentinel final PASS.

## Exact MVP acceptance checklist for being better at execution/trust

OneHub can claim MVP superiority at execution/trust only when all of the following are true and Sentinel verifies them on the canonical private-pilot target.

### A. Positioning and promise

- [ ] User-facing copy says OneHub is an event operating system for execution/trust, not primarily a wedding website, registry, invitation suite, or generic vendor directory.
- [ ] Comparison copy explicitly avoids claiming better registry, invitation design, website polish, marketplace scale, legal approval, escrow approval, or live payment status unless separately proven.
- [ ] The private-pilot boundary is visible where relevant: demo/pilot readiness is not public launch approval.

### B. Event-attached discovery to request

- [ ] A Pro Planner and DIY Planner can start from a selected event and reach marketplace discovery without losing event context.
- [ ] Authenticated marketplace pages do not show public "Sign in" / "Create account" navigation to signed-in users.
- [ ] Provider/venue cards distinguish verified on-platform listings from unverified/copy-only leads.
- [ ] No fallback item can claim "verified" or carry a fake listing id if it cannot be shortlisted/requested as a real listing.
- [ ] Shortlist and booking request actions persist against the selected event and real listing/provider context.
- [ ] Legacy or remembered request links are protected by either a redirect from `/app/requests` to `/requests` or updated references with no 404 for the pilot flow.

### C. Provider-backed proposal gate

- [ ] A vendor/venue can respond to a booking request with a provider-submitted proposal or provider-confirmed quote that becomes a non-draft proposal record.
- [ ] Proposal records include enough evidence for buyer trust: provider/listing identity, event, scope, line items, milestone/payment schedule, submitted timestamp, and provider-backed status.
- [ ] Buyer-side users cannot approve AI-generated or planner-generated `DRAFT` proposals as if they were provider commitments.
- [ ] Proposal detail pages clearly label draft, provider-backed, accepted, rejected, and needs-revision states.
- [ ] Proposal approval is blocked unless the proposal is non-draft, provider-backed, event-attached, and visible only to intended participants.

### D. Contract gate

- [ ] Accepted provider-backed proposal can generate a contract without losing event/listing/provider context.
- [ ] Contract UI tells each participant whether the contract is draft, issued, awaiting buyer signature, awaiting seller signature, partially signed, fully signed, or not payment-ready.
- [ ] Contract detail pages are server-authorized before render.
- [ ] Unrelated authenticated users receive safe 403/404 copy and cannot read commercial terms by known ID.
- [ ] The UI does not imply legal approval or public enforceability beyond the approved MVP/private-pilot boundary.

### E. Payment-readiness truth

- [ ] Payment entry is hidden or disabled until provider-backed proposal acceptance and required signatures are complete.
- [ ] Payment UI distinguishes setup/readiness from live charge, held/internal review, payout, refund, and release.
- [ ] Stripe Connect/setup copy states setup only and does not imply live charges, payouts, or release without OneHub approval/manual review.
- [ ] No screen says money is paid, held, escrowed, refunded, released, or sent unless the backend/provider state proves it.
- [ ] Live payment activation remains blocked until founder approval, credentials/configuration, legal/payment review, and Sentinel verification.

### F. Communication and notification truth

- [ ] Messages are available from core role dashboards and event/commercial contexts.
- [ ] Invite UI says exactly what happened: copy prepared, draft queued, not configured, failed, or sent.
- [ ] If email/SMS sending is not implemented or configured, user-facing copy says no email/SMS was sent by OneHub.
- [ ] Notifications reflect real created events/messages/tasks/contracts and do not imply external delivery without provider proof.

### G. Milestones, tasks, and accountability

- [ ] Event workspace shows what is due, who owns it, what is blocked, and what is complete.
- [ ] Provider/venue sees only its obligations and related commercial records.
- [ ] Client sees safe shared/pending event context and next actions without planner edit surfaces.
- [ ] Admin sees overdue/blocked/high-risk items across events.
- [ ] Status survives refresh and is not only client-side decoration.

### H. Crisis execution baseline

- [ ] A planner/admin can record a provider cancellation or execution problem.
- [ ] The issue view shows affected contract, payment-readiness state, milestone/task impact, and owner.
- [ ] Relevant participants can be notified inside OneHub without false external-send claims.
- [ ] Replacement providers can be surfaced as available/requestable candidates tied to the same event.
- [ ] Replacement request -> provider-backed proposal -> contract path can start without losing event context.
- [ ] Refund/redirection/release copy remains manual-review/payment-approval safe.

### I. Admin oversight and audit

- [ ] Admin can inspect trust/risk queues for disputes, refunds, holdbacks, payouts, failed sends, abuse, role/account issues, and high-risk events.
- [ ] Admin actions have clear status, owner, timestamp, and audit copy.
- [ ] Admin UI does not imply automatic money movement or legal approval.
- [ ] Support escalation forms ask for exact event/provider/contract/blocker context, not vague screenshots.

### J. Role-route coherence and empty states

- [ ] Admin, Pro Planner, DIY Planner, Client, Vendor, and Venue can sign in and land on a useful role-specific dashboard.
- [ ] Each included MVP route has either useful data, a useful empty state, or a safe denial state.
- [ ] No authenticated role sees public sign-in/create-account CTAs as primary navigation.
- [ ] No role is told to create records it is not supposed to create.
- [ ] Client pending-share state includes waiting language plus `Open Message Inbox`/contact path and `Back to dashboard`.
- [ ] Pro Planner settings do not route to vendor/venue-only billing denial copy without an explicit role boundary.
